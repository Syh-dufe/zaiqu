# LLM调用改进：诊断与可执行的下一轮设计

## 已确认的问题

1. 首轮告警把正常Merton变化当成事件，五个冲击回合都提前调用了API。另抽20条正常验证需求，旧检测器仍有18条报警，问题不局限于最初五条。
2. 当前仅校验规则语法和动作范围，未在执行前评价闭环后果。生成的规则可以合法但性能退化。
3. 提示词主要描述下游积压及库存，未完整描述作者串行状态更新和上游欠单/发货联动。冲击中区域节点平均积压由11.937升到23.223，LLM对上游159个节点期减单、仅1个节点期加单。这是已观察到的联动退化和动作统计，不能直接断言唯一因果。
4. 当前只给在途总量及下次到货，丢失了剩余各期已知到货结构。需要补全已知在途四个槽位、历史真实发货与订单、各节点成本拆分。已知在途不是未来未知需求。
5. 五组相同输入分别生成不同规则，说明单次生成存在随机性；首轮LLM自己的正常/冲击配对不是同一规则的严格配对。

## 独立检测诊断（未调用API）

正常校准集种子20261007，50条；正常验证种子20261008，20条；冲击开发验证底层种子20261009，事件种子20261010，20条。采用原Merton、1.5倍截断20、随机开始60..100、持续20..40。完整数据与统计保留在artifacts/llm_improvement_diagnostics。

候选检测器对正向log需求变化按此前20个变化标准化（sigma下限0.05），并要求下一次需求仍达到跳变前1.2倍；阈值为50条正常序列候选最大分数的95%分位数5.53824。只用正常校准数据确定阈值，没有用冲击结果调阈值。

| 统计 | 旧检测器 | 候选检测器 |
| --- | ---: | ---: |
| 正常验证20条出现告警 | 18 | 0 |
| 冲击前已告警 | 14 | 1 |
| 冲击窗口内首次告警 | 4 | 4 |
| 全程无告警 | 1 | 14 |
| 冲击结束后首次告警 | 1 | 1 |

候选不能称为已修好：误报少但漏报多。20条验证不足以保证误报率；本批数据现已用于开发观察，不能重复充当最终测试。

## 三种改进方向

- 仅丰富提示词：改动少，但没有结果反馈，不能阻止合法坏规则。
- 开发阶段生成-评价-变异：接近VRPAgent原方法，有助于发现规则，但优化的是开发集表现，需要新的独立测试，且它属于规则适配。
- **推荐：有限候选 + 因果预测仿真评价 + 反馈修订 + 原策略回退。**保持HAPPO冻结，事件发生后适配规则。先用小版本，不直接启动大规模遗传搜索。

参考依据是VRPAgent第4节的算子生成、仿真适应度和变异反馈；它没有直接提供我们的在线库存应对系统。

论文：https://arxiv.org/html/2510.07073v1#S4

## 下一轮最小方案（设计，尚未执行/调用API）

### 1. 告警接口单独明确

如果业务允许现场灾情通报，可将“通报已发生”作为可观测事件输入，各对照获得同一通报、同一延迟，不提供未来需求和持续时间。该通报可靠性与延迟是新假设，必须明确，而不能偷偷用仿真事件表充当自动需求检测。

如果业务只允许需求历史，则先另做正常数据校准及新事件检出/延迟评估，达到预定标准再测试事件后规则生成。当前候选未达可用结论，不据此开展有效性宣称。

### 2. 改进上下文而不改变环境

提供原物资流动与欠单结转的准确数学说明，给出当前三节点库存/积压、各期在途到货、已发生的需求/订单/发货历史，以及HAPPO建议。提示词明确全系统原成本是主要评价项，下游累计积压是额外服务指标，不能把压力转移到上游而不计成本。

### 3. 预算受限的规则迭代

先用2条新需求，各有正常/冲击情形，作为实现检查；暂不做正式显著性检验。每个需要介入的情形最多3次生成请求，四个情形最多12次，无限重试和超预算调用禁止。

- 请求1生成3个有不同机制的候选算子，输出仍为受限JSON表达式。
- 分别在相同预测需求上评价候选、原HAPPO（零修正）和人工规则。
- 请求2给DeepSeek返回候选的模拟成本、各节点积压和失败情况，让它改进一个候选，而不是只要求“更好”。
- 留出一批新的预测样本复核修改结果；不能只在用于反馈的样本上评分。
- 最多再作一次请求3。全部候选与失败保存，预算用完停止。没有通过评价的修正就执行零修正，不强制LLM获胜。

### 4. 严格限制预测评价的信息

影子仿真只从已观察的库存、积压、在途、动作历史及HAPPO recurrent状态初始化。预测需求由历史构造，不能从真实环境对象复制完整未来需求。候选使用相同预测样本；预测本身另行记录和检查误差。

初始预测窗口建议20期以涵盖多个提前期的联动。每5期重新评价一次以控制计算量；先计时再扩充情形数量。API时间、影子仿真时间和真实决策等待假设都需要报告。

### 5. 接受、回退与停止

原HAPPO始终在候选集中。预先固定预测全系统成本与下游积压的接受条件，修订候选不能只依据解释文本。预测评价并不保证真实改善；部署后使用已发生结果监测，恶化则停止修正。所有对照使用相同状态信息、预测预算、动作限制及告警条件。

## 公平比较与后续

正式验证至少需要原HAPPO、人工规则+相同预测筛选、LLM单次规则、LLM迭代+筛选，以区分LLM贡献和额外计算/筛选贡献。小试可先检查两个情形的接口与时间，再扩展；此处没有提前指定胜者。

开发中看过的事件用于分析和改进，最终效果在另行固定的新事件及多次生成上报告。HAPPO无需重新训练；LLM规则生成与评价发生了适配，不可称整个系统零适配。
