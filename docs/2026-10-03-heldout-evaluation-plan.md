# 固定 HAPPO 模型的新需求小型评估

用户已确认先冻结模型、用新模拟需求评估，再考虑灾区需求冲击。采用原 Merton 生成器，相比直接加冲击更能先隔离需求抽样变化；相比立即重新训练，冻结模型能避免使用新评估结果选择参数。

## 固定设计

- 原库存规则和原 CRunner.eval 不改动；读取已经保存的训练配置。
- 模型提前指定：官方最佳 250,000 步及最终 295,000 步，各三节点 actor/critic。校验参数摘要，评估前后保持不变。
- 新需求种子 20261003；20 条原生成器 merton(200,20) 序列，保存全部 201 个值。原评估循环仅使用前 200 个值，包括首值；不改变索引或终止处理。
- 先在原 20 条需求上核对成本 23.71875 和 25.3859166667，再在相同的新 20 条需求上评估两个固定模型。不根据结果重抽需求或更换模型。
- 新需求与原评估需求的实际 200 期内容摘要不得相同。独立随机生成未读取训练需求；这不等于有逐条训练需求日志的完全去重证明。
- 记录逐期库存、积压和原评估奖励，输出逐需求平均成本、成本离散程度及各节点平均库存/积压。积压指标不称作准时满足率。
- 无基线排名、重新训练、洪灾冲击或 LLM；20 条需求仅为小型泛化检查，不能给出跨训练种子稳健性结论。

## 实施计划

1. 创建 experiments/heldout_evaluation/run.py：加载训练配置和完成审计，校验原仓库版本及源码，生成固定需求并保存摘要。
2. 使用原 DummyVecEnv 与 CRunner.eval；仅以观测包装记录逐期结果，固定评估数据。禁止调用 train/run/compute。
3. 核对原评估成本、每条 200 期和参数不变；运行新需求评估，保存完整 CSV/JSON，不覆盖已有目录。
4. 汇总全部 20 条需求，记录局限、更新文档并上传自有脚本及小型评估产物。模型和作者源码继续保留本地。

评估本身及原结果一致性核验是本次获授权的实验验证。无需增加与此实验无关的单元测试。按本聊天既有 GitHub 管理方式提交和推送。
