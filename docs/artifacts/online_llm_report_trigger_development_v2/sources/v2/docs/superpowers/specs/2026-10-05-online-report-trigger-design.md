# 按已送达报告分配实时LLM调用机会：开发设计

用户已经授权跨冲击确认完成后，根据不足继续改进。v5b确认与全部原始产物已经审核、推送；总体有效，但各类型成本证据不足。本设计依据该授权继续，保持原库存环境、五个HAPPO模型及原实时LLM生成/解析/预测筛选逻辑。

## 已确认的问题和假设

原控制器在通知后的5期时槽连续触发，四次生成通常集中在前20期；其后只筛选最后的候选库。双峰的第二峰、持续需求的后期和需求回落阶段可能缺少新的候选。源码支持这个时间分配问题，但目前没有证明它造成成本退化。

三个可行方向：改调用时机（隔离单一机制，先做）；改预测器（会同时影响搜索与复核，另登记）；改格式契约（历史小批未优于原版，当前不合并）。本轮只改变生成事件的时机。

## 通用调度

方法名 `report_trigger_feedback`。首次通知在与原方法一致的时槽触发。之后仍每5期筛选，生成最多四次。新增生成要求有新送达报告、距离上次生成至少20期，且满足以下任一条件：

1. 最新两个完整报告的均值与上次生成时同样计算的参考值相比，绝对变化除以 `max(1, abs(参考值))` 至少25%；
2. 距离上次生成至少30期（防止低信号长期不更新）。

报告不足两条时使用已有报告均值，无报告时为0；仅使用 `demand_mean`，不访问隐藏需求或事件类型。参考值在每次生成后更新。没有新报告时不能生成。筛选时槽由首次通知确定，实际decision_period仍为环境step_num+1。20/30期和25%是事前开发选择，不称文献最优或真实校准参数。所有调度条件与报告值记录在scores里，供独立核验。

为隔离时机：原SYSTEM、Client、格式修复、候选0反馈替换、3+3预测路径、筛选门槛、5期修正、回合清空记忆全部保持原样。除新方法调度外，原HAPPO与online_feedback走原控制器，不能让新方法替换原代码。最大API预算匹配，实际调用次数可能不同，需报告而不能称实际计算完全相同。

## 开发输入与方法

固定复用v5b已完成的batch01与batch06，五模型种子11—15全部纳入。这两批各有四类路径，合计每类2条不同路径。该选择在任何新方法结果产生前固定；v5b既有确认成绩保留独立确认身份，但这些路径对升级版改为已用开发资料。

三方法 `happo / online_feedback / report_trigger_feedback`，正常与冲击配对，共240回合、144,000节点期；不得把40个模型×路径配对称为40条不同需求路径。原online_feedback也重新调用API，回复具有随机性，改进差不能全归因于调度，原v5b成绩只作历史。

每冲击LLM回合最多16HTTP，80个此类回合，首轮硬上限1280HTTP/640语义请求；每任务额度恢复最多一次，含恢复累计2560/1280。这只是本批预算，非用户总API授权上限。认证权限或程序/审核错误停止诊断；402保留原始记录、每30分钟查可用性，恢复后对应任务最多一次完整重跑。

## 评估与下一步

共同目标成本与欠货，配对汇总总体、四类、全部五种子及所有退化，记录调用时刻、时机条件、实际执行修正、失败、tokens、预测开销。开发样本小，不作显著性或独立泛化结论。

只有新方法相对本批原online_feedback的总体成本与欠货都严格下降，且四类中没有任何一类两个指标同时增加，才进入新未见路径确认；其他结果先记录失败机制，不放宽门槛。如果不合格，不启动正式确认。最多先执行本轮一个预登记方案，不在同输入上反复调整20/30期或25%直到胜出。新确认方案另登记，不复用本批输入，不向提示优化反馈新确认成绩。

## 实现和审核边界

新增独立文件夹 `experiments/online_llm_report_trigger/`；冻结v5/v5b/online_llm的所有现有源码不改。新controller保存原控制器源码SHA并仅覆盖触发调度；新runner对原方法调用原实现，对新方法调用新controller。批驱动逐任务核验源码、输入、模型、提示与方法契约。

无API预检需核对：首次触发相同、无新报告不调用、最小20期间距、最长30期等待仅在合法时槽且有新报告生效、四次上限、回合重置、原方法源码与提示恒等。正式运行后按原始节点期复算240/144,000、正常和通知前动作一致，并独立检查每个触发满足已登记条件。独立归档后才决定新确认。密钥只读Windows用户环境，脱敏与缺席检查继续。
