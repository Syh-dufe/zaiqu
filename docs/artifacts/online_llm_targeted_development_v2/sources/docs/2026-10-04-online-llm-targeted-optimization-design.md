# 实时LLM针对性优化：诊断与方案初稿

状态：用户于2026-10-04确认“开始”，本方案已批准，独立版本正在实施；尚未启动新训练或付费API实验。

## 目标与数据用途

HAPPO继续冻结，库存机制、k=3信息边界、通知延迟和冲击分布不变。优化现场规则生成和修订，不为每条灾情预训练LLM。后续不安排随机候选对比。

本次诊断使用已结束的confirmation_v1。因为其结果用于提出新机制，该数据现在是已用开发/诊断数据；原冻结v1的独立确认结论保留，新版本不能把它重复称为未见测试。

## 全量记录诊断

从25个子任务的calls.json和scores.json检查全部记录，无API和环境重放。

- HTTP共1069次，91次格式失败：63次unknown feature、27次expected one to four rules、1次Incomplete output。11次初始生成修复后仍失败。原始请求与回复不修改。
- 实施前进一步解析63条unknown feature失败回复：全部非法名称均为DSL中的小写true，共166次出现。这是JSON布尔值与Python式表达式字符串的混淆，不是模型发明了63个库存特征。新提示应明确when使用字符串True，并给出合法JSON样例；不改原解析器，也不自动改变生成表达式语义。
- 实时反馈400次生成事件，11次生成失败；其余389次中，替换候选0后预测成本83次降低、70次升高、236次持平。不能把搜索预测变化解释为实际未来收益。
- 13次修订使满足搜索门槛的最佳候选成本变差或不再存在；其中11次丢掉原本合格的候选0，7次丢掉所有合格候选。独立复核仍能回退HAPPO，但不能找回被删除的原候选。
- 一次生成方法100事件中，修订预测成本22次降低、11次升高、67次持平，1次最佳合格选项变差。
- 实时反馈2385次筛选仅305次执行非零修正，一次生成2385次筛选278次执行非零修正。低执行率可能来自候选质量、预测或严格门槛，不能未经诊断就放宽门槛。
- 当前控制器每个新生成事件覆盖旧候选库，没有跨事件保留上一执行候选。保留是否有益尚无反事实实验证据，不把这个代码特征直接称为已证实原因。

修订前后搜索使用同一状态与预测路径；原候选1/2与零基线的记录逐项相同，只有候选0被替换，因此上述搜索选项损失可以直接核对。

## 三种优化方向

1. **仅修复输出契约**：提示明确合法特征与合法JSON示例，格式修复反馈明确字段/名称限制。改动少，但不解决修订丢掉有效候选的问题。
2. **输出契约＋保留优选候选（推荐）**：增加上述约束，在本轮搜索中保留最佳合格候选，修订替换最弱的非保留候选；后续生成事件另保留一个上次实际执行的候选供当前状态重评。更直接对应已观察的损失，但跨事件保留可能限制探索，必须评估。
3. **更换需求预测或调用触发**：可能改善适应性，但同时改变多项机制，计算预算与归因更复杂。暂不作为本轮首选。

## 推荐方案的边界

- DSL仍使用原10个局部特征，保留1至4条规则、先匹配优先、动作截断；不开放任意Python或隐藏需求。
- 初次事件生成3候选。后续事件若存在上次实际执行的非零候选，保留1个并生成2个新候选；没有则生成3个。总候选数固定3，另有零修正基线。
- 保留候选仍在当前状态重新评分和独立复核，不因历史有效直接执行。只有实际执行过的候选身份与因果状态可进入上下文，不给API独立复核分数。
- 反馈修订先按原门槛确定本轮搜索最优候选；保护该候选，要求LLM针对一个较弱候选输出替代，候选总数不增加。没有合格候选时，保护搜索成本最低的有效候选；无有效候选则使用零修正。
- 不提前评价修订质量后再多次调用；仍每事件一次生成、一次修订。初始/修订最多各一次格式修复。
- 每5期筛选、最多4生成事件、每回合16HTTP、20期预测和前5期修正、3搜索＋3独立复核、1%成本门槛与欠货不增均不变。
- 不修改v1登记源码和归档；新版本使用独立模块与新输出路径，记录所有差异。

## 首批小型开发实验建议

2模型（11、12）×4条新开发路径×4方法×正常/冲击，共64回合、38400节点期。

方法：纯HAPPO、原实时反馈v1、仅输出契约修复、输出契约修复＋优选候选保留。保留所有方法的合法失败与回退。三种LLM方法各最多16HTTP/冲击回合，本批合计最多384HTTP，为批次上限，不是用户总API授权上限。

新开发需求/事件种子建议20271001/20271002，冻结登记后生成并核对全部历史路径。任何碰撞或异常均保存诊断，不根据结果删换路径。所有方法使用相同输入、模型、触发与预测路径；API输出有随机性，不能假定相同调用产生相同候选。

诊断指标：成本、下游欠货、合格候选丢失、候选保留/执行率、格式失败与回退、请求数/tokens/墙钟。开发中优先选择相对原实时反馈平均成本下降且欠货不升的机制，并报告逐模型和逐路径退化；这只是开发筛选标准，不是正式显著性判断。

小实验后决定是否扩大；最终冻结提示、代码与预算，再登记新的5×20确认路径。确认不向开发反馈成绩。不承诺新机制一定优于原版本。
